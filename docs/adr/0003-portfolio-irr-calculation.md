# ADR-0003: Portfolio-wide IRR calculation

## Status
Accepted

## Context
Users want a single "how am I actually doing" return metric across all their holdings, computed from all buy/sell transactions and dividend income, in the presence of multiple asset currencies and irregular transaction dates. This requires solving XIRR (money-weighted return with irregular dates), which in turn requires historical currency conversion — a capability the app does not currently have (`Boonorbust2.ExchangeRates` only caches *live*, current-moment rates).

## Decision

**Scope**: One single portfolio-wide XIRR per user, across all transactions for all assets. Not scoped to the app's existing named `Portfolio` (tag-grouping) concept — a given asset can belong to multiple named Portfolios via tags, so cash flows don't partition cleanly across them. Per-asset or per-Portfolio IRR is out of scope for now but can be layered on later using the same building blocks.

**Cash flows** (in chronological order, all converted to the user's `Accounts.User.currency` preference):
- Every `PortfolioTransactions.PortfolioTransaction` with `action: "buy"` → negative flow, dated at `transaction_date`, amount = transaction's `amount` (already includes commission)
- Every `action: "sell"` → positive flow, same basis
- Every `RealizedProfits.RealizedProfit` with a non-nil `dividend_id` → positive flow, dated at the associated `Dividend.pay_date`. This is included deliberately: a dividend is return generated by the asset itself (it doesn't change `quantity_on_hand`/cost basis, per `PortfolioPositions`), unlike external capital such as salary. Reinvesting a dividend into a later buy is not double-counting — it is two independent crossings of the "your pocket vs. the portfolio" boundary.
- Today's total portfolio value → final positive flow, dated today, computed fresh via `PortfolioPositions.calculate_total_portfolio_value/2` over `PortfolioPositions.list_latest_positions/2` (the same logic the Dashboard already uses), converted at today's *live* rate. This automatically contributes `$0` for fully-divested assets (`quantity_on_hand` is 0).

**Currency conversion**: each historical cash flow is converted using the exchange rate **as of that flow's own date**, not today's rate — a deliberate deviation from how the rest of the app converts historical amounts (e.g. `Dashboard.enrich_single_position/3` converts cost basis at today's rate). Historical rates are sourced from the [Frankfurter](https://frankfurter.dev) API (`GET /v2/rates?date=YYYY-MM-DD&base=<reporting_currency>&quotes=<currencies needed that day>`) — free, no auth, supports direct SGD/USD/etc. bases, and returns a rate even for weekend/holiday dates.

**Persistence**: a new `historical_exchange_rates` table, keyed on `(date, base_currency)`, storing the full quotes map returned by Frankfurter for that day (mirroring the shape of the existing in-memory live-rate cache). Fetched lazily, once per unique `(date, base_currency)` actually needed by a user's transaction/dividend history; never refetched afterward, since historical rates are immutable.

**Failure handling**: if the historical rate fetch fails for any date needed by the calculation, the entire IRR calculation fails (no fallback to today's live rate for that one flow, and no silent exclusion of the affected cash flow). This is a stricter policy than the live `ExchangeRates.convert_money/2` fallback-on-error behavior used elsewhere in the app, chosen because a silently-approximated or silently-incomplete IRR is worse than a visible failure for a number that claims to represent "your actual return."

**Solver**: a small hand-rolled bisection-method solver in a new `Boonorbust2.Irr` context module — no third-party dependency. The two existing Hex options (`ex_xirr`, `xirr`) are small/low-adoption packages with thin, inconsistent documentation, unclear edge-case behavior, and float-only APIs; bisection over NPV is simple enough (~40 lines) that owning it directly, with explicit `@spec`s and explicit handling of "no sign change" cases, is preferable to depending on an unmaintained library for a number this central to the feature.

**"No valid IRR" handling**: explicitly detected and surfaced as `{:error, :reason}` (e.g. all cash flows same sign, or all cash flows fall on the same day so NPV doesn't vary with rate) — the UI must show an explicit "not enough data" / "IRR unavailable" message in these cases. Never fabricate a `0%` result and never silently hide the IRR section.

**UI placement**: rendered on the existing Dashboard, computed via LiveView `assign_async` so a cold historical-rate cache or a Frankfurter outage never blocks the rest of the dashboard from rendering. Shows a loading state, then either the computed percentage or the explicit unavailable message.

## Consequences
- Accurate multi-currency IRR requires one Frankfurter API call per previously-unseen `(date, base_currency)` pair; first-time cost is bounded by cache growth per historical date, not per calculation, since rates never change
- A Frankfurter outage makes IRR temporarily unavailable, but — because it's computed via `assign_async` — does not affect the rest of the dashboard
- Historical-rate-based conversion is more accurate than the rest of the app's existing today's-rate convention (see ADR-0002 and `Dashboard.enrich_single_position/3`), so this feature is intentionally inconsistent with that precedent; a future refactor could migrate other historical valuations (e.g. cost basis) onto the same historical-rate table for consistency
- No per-asset or per-named-Portfolio IRR breakdown yet; adding it later can reuse the same cash-flow-assembly and solver code, filtered by `asset_id` or by the assets in a Portfolio's tags
